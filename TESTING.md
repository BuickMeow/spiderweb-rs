# Testing guide (TESTING.md)

Run this before sharing a build or opening a pull request. Three layers:
**automated tests → manual GUI checklist → performance measurements**.

## 0. Quick check (after every change / before posting)

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --release -p spiderweb-app
```

## 1. What the automated tests cover

| Layer | Contents | Location |
|---|---|---|
| Core differential tests | 3000+ cases generated by the original Python engine (incl. joined.py / convert.py) | `crates/spiderweb-core/tests/*_vectors.rs` + `tools/gen_*_vectors.py` |
| Domino codec | interoperates with Python (encoded payload byte-identical / Python data decoded) | `crates/spiderweb-domino/tests/` |
| MIDI export | **byte-identical** to the Python original (hand-written SMF header check, no MIDI library) | `crates/spiderweb-io/tests/midi_vectors.rs` |
| Project writer | 12-significant-digit rounding (`project.short_shape`, tumour graphs included) matches Python | `crates/spiderweb-io/tests/short_vectors.rs` |
| App unit tests | input state machine, curve handles, scrub, i18n keys, 256-key mode, custom semantics, join/split commands (incl. back to the old shapes), turn into live shape, drawer undo/redo, tumour window logic, snap steps / custom snap window, history steps / jump, tips queue | `#[cfg(test)]` in `crates/spiderweb-app/src/**` |

Current baseline: all workspace tests green, `clippy -D warnings` clean,
core micro-benchmarks in section 3.4.

The differential generators run against the Python reference. Point them at
the upstream copy you are porting:

```bash
SPIDERWEB_SRC=/path/to/upstream/scripts python3 tools/gen_paths_vectors.py
```

## 2. Manual GUI checklist

Run it after large changes; mention "manual interaction test passed" in the
release notes and keep the filled-in list.

- [ ] Every tool: Line / Polyline / Freehand / Curve / Arc / Square / Circle /
      Triangle / Custom / Funnel / Text (draw, drag points, delete points,
      undo/redo, re-select)
- [ ] Select: click / Ctrl multi-select / drag / handles / Delete / Duplicate / Ctrl+A
- [ ] Right-click menu, double right-click toggles Select ↔ last drawing tool
- [ ] Snap dropdown: the note pictures (dotted ones with a dot, triplets with a 3),
      `Custom…` (count / dotted / divided by, the length line, out-of-range in red);
      the grid and dragging follow the chosen step; an old project's `1/64` opens
      as a custom snap
- [ ] Project → Domino start: copy with "First note at tick 0" and with "From the
      bar line", and paste with both
- [ ] History (toolbar): every edit shows as a named step, click one to go back /
      forward, Undock / Dock and closing the window dock it again
- [ ] Turn into live shape (Ctrl+L / right-click / Custom panel button): notes and
      channels stay the same, the warning shows for tumours / "last note", one
      custom shape already can't be turned
- [ ] Split into separate shapes (Ctrl+Shift+G): a live shape goes back to the old
      shapes after a plain move (right-click label says "Split back into the old
      shapes"); resizing / turning / editing a stroke falls back to splitting the
      drawing into groups of touching strokes
- [ ] Playback (Space), right-drag listening, playhead page turning
- [ ] MIDI export (open the file in a DAW or in Domino)
- [ ] Copy to / paste from Domino (**Windows only**; on macOS the buttons must
      report that, not crash). With `Keys: 256`, keys 128–255 must survive a
      copy into a Domino 256k build.
- [ ] Open a 1.1.0 / 1.2.0 `autosave.json`, Save As and re-open, autosave backup
- [ ] Drawer: draw a shape, save it to the library (`shapes/*.json`), Use it,
      place it on the roll
- [ ] Tumour window (panel button / right-click Tumours…): settings follow the
      selection, rotation / slant, the graph editor (drag / click to add / right-click to
      remove, presets, formula), Cancel puts the graph back
- [ ] Velocity pane: Linear / Curve / Pencil, Enter confirms
- [ ] Help (F1, searchable), first-use tips, `errors.log`
- [ ] Window resize, Retina (ppp ≠ 1), side panel scrolling, second monitor
- [ ] Big-project smoke test: ≥ 1M notes, drag / play / undo without crashing

## 3. Performance measurement

Always release builds. Record machine model / OS / resolution / Retina.
Report p50 / p95 / max frame times, not just averages.

### 3.1 Generate a bench project

```bash
python3 tools/gen_bench_project.py --notes 1000000 -o bench.json      # 1M
python3 tools/gen_bench_project.py --notes 5000000 -o bench-big.json  # 5M
```

Copy the result next to the executable as `autosave.json`, or open it with
Open… in the app. Both this port and the original Python read the format.

### 3.2 Turn on the perf HUD

```bash
SPIDERWEB_PERF=1 cargo run --release -p spiderweb-app
```

- HUD (top right): frame-time EMA, shape count, note count
- stderr: `[perf] load+render … ms`, `[perf] shapes_changed … ms`

### 3.3 Record table (same-screen performance)

Measure the 5M project, then put the numbers in the release notes:

| Scenario | p50 | p95 | max | Notes |
|---|---|---|---|---|
| Idle | | | | |
| Pan / zoom | | | | wgpu path should only touch uniforms |
| Drag a shape | | | | instance buffer re-upload: worst frame |
| Playback | | | | |
| Load project (to first frame) | | | | `[perf] load+render` |
| RSS | | | | `ps -o rss= -p $(pgrep -f spiderweb-app)` |

### 3.4 Core micro-benchmarks (tracked in CI)

```bash
cargo bench -p spiderweb-core --bench engine
```

Reference values (Apple Silicon, release — for trend comparison only):

| Case | Time |
|---|---|
| line_notes_64keys | ~6 µs |
| tumour_line_64keys | ~0.66 ms |
| custom_spam_100k | ~1.8 ms |
| funnel_spam_100k | ~4.7 ms |
| render_single_100k | ~2.5 ms |

## 4. CI and "let everyone see the performance"

Two workflows are configured:

- **`.github/workflows/ci.yml`** — on push / PR: `fmt / clippy -D warnings /
  test / release build` on Ubuntu + macOS + Windows. Add the badge to the README.
- **`.github/workflows/bench.yml`** — on `main` it runs the core benchmarks and
  uses [benchmark-action](https://github.com/benchmark-action/github-action-benchmark)
  to store one data point per commit on the `gh-pages` branch and comment on
  regressions in PRs (threshold 130%).

Enable the dashboard (one-time, in the repository settings):

1. Settings → Pages → Source: **Deploy from a branch** → branch `gh-pages`,
   folder `/ (root)` (the branch is created by the first benchmark run).
2. Dashboard URL: `https://<user>.github.io/<repo>/dev/bench/`
   (this repository: `https://buickmeow.github.io/spiderweb-rs/dev/bench/`).

That is the most convenient way to show performance to everyone: **one URL,
a trend line over commits, automatic PR comments**. Optional upgrade:
[CodSpeed](https://codspeed.io) (free for open source, flame graphs in PRs).
